# План перехода: «генератор с захардкоженными данными» → «генератор + конфиг»

Цель: из `raiv-fish-bot/generate_*.py` получить ядро, которое собирает бота по `platform/clients/<client>.json` (схема — `platform/CONFIG_SCHEMA.md`). Работающий бот @RAIV_FISH_bot при этом не ломается ни на минуту.

## Исходное состояние (01.10.2026, проверено по репозиторию)

| Что | Где | Состояние |
|---|---|---|
| Живой бот | Make, сценарий 7707233 | **v6** (витрина, слоты, статусы, оценки, рефералка, мин. 20 €) |
| Генератор v6 | ветка `origin/claude/blissful-tesla-9xox1x` (руководитель проекта) | совпадает с живым ботом, бэкап `backup/v6_miniapp_blueprint.json`, откат — `v5_stage1_blueprint.json` |
| Генератор в этой ветке / main | `raiv-fish-bot/generate_blueprint.py` | **v4** — устарел, загружать нельзя |
| Каталог | `cats` в `generate_blueprint.py` → вшит в blueprint через `switch()` (дважды: обычный поток и корзина из витрины) | **в data store не перенесён**; витрина собирается из того же `cats` (`generate_miniapp.py`) |
| Другие генераторы | `generate_pro.py`, `generate_daily_report.py`, `generate_abandoned.py`, `generate_miniapp.py` | импортируют `generate_blueprint.py` через `exec` (побочный эффект: пишут `/tmp/_bp_tmp.json`); `generate_daily_report.py` дублирует ID вручную |
| Дыры аудита v5 (A1–A15) | `agents/ux_audit_log.md` | в генераторе v6 закрыты частично (обработчики ошибок на части отправок, проверки рефералки); `secret_token`, дубли заказов, сумма из корзины, бонусы до доставки, промокоды, проверка нажавшего кнопку — **открыты** |

Главный риск всего проекта — **расхождение** между Make и генератором: всё, что правится в Make руками, теряется при следующей загрузке из генератора (так уже было с v5). Поэтому первая половина плана — «ноль изменений поведения», вторая — изменения только через тестовый бот.

## Правила, которые действуют на всех шагах

1. **Нулевой diff до изменения поведения.** Шаг рефакторинга считается готовым, только если нормализованный blueprint из «генератор + конфиг» равен эталону (golden) байт в байт. Такой шаг вообще не требует загрузки в Make.
2. **Любое изменение поведения — сначала тестовый бот**, потом живой, с бэкапом и проверенным откатом.
3. **Один владелец файла.** Пока руководитель проекта правит `raiv-fish-bot/generate_*.py`, архитектор их не трогает (только читает). Передача — явная («беру generate_blueprint.py до …»).
4. **Правка в Make = правка в генераторе в тот же день.** Иначе следующий релиз её сотрёт.
5. В репозитории — только ID и `secret://`-ссылки. Перед коммитом — проверка на токены и URL хуков (CHK-15).

## Фаза 3. Стандартные проверки ядра (CHK) — 28–34 ч

Каждая проверка — отдельный коммит в генераторе, golden обновляется осознанно (diff показывает только ожидаемые модули), прогон чек-листа на тестовом боте. В живой бот — пакетами (фаза 4).

| Пакет | Проверки | Часы | Примечание |
|---|---|---|---|
| P1 «Безопасность» | CHK-01 secret_token + новый хук, CHK-09 кто нажал, CHK-11 sequential, CHK-15 | 4–5 | Ротация хука — один раз, совместно с руководителем: новый хук → `setWebhook(url, secret_token)` → проверка → удалить старый. |
| P2 «Деньги» | CHK-01a дубли + счётчик номеров, CHK-03 сумма из корзины, CHK-04 единицы и лимиты, CHK-06 промокоды 1–50 %, CHK-07 пересчёт | 8–9 | Совпадает с топ-2 аудита v5 (~5 ч) — не делать дважды: кто первым берёт, делает **в генераторе**. |
| P3 «Бонусы» | CHK-05 бонусы после доставки, рефералка после доставки | 3–4 | Миграция данных: уже начисленные бонусы остаются; новые — `pending` до статуса «доставлен». |
| P4 «Оплата» | CHK-08 Stripe: видна только владельцу в test, сверка заказа/суммы, `async_payment_succeeded` | 3 | Сценарий 7707560. |
| P5 «UX-надёжность» | CHK-02 обработчики + `answerCallbackQuery`, CHK-12 слоты, CHK-13 телефон/адрес, CHK-14 предпросмотр рассылки | 4–5 | |
| P6 «Данные» | CHK-10: согласие на рассылки, /privacy, /delete (анонимизация), сценарий `retention_cleanup`, AI без имён | 6–8 | Нужны тексты владельца (Impressum, контакт). Существующая база — без рассылок до согласия (`existing_customers_without_consent: no_marketing`), это решение владельца. |

## Фаза 4. Релиз в живой бот — 1 ч на пакет

Порядок на каждый релиз:

1. **Бэкап**: Export текущего живого blueprint → `backup/v<N>_live_<дата>.json` (не доверять старым файлам — вдруг правили руками).
2. **Diff**: `bp_diff backup/v<N>_live.json bp_new.json` — изменились только модули пакета. Неожиданное — стоп.
3. **Тестовый бот**: чек-лист пройден на этой же сборке (тот же конфиг, кроме `infra`/`channels`).
4. **Окно**: днём в будни, когда руководитель не правит бота, не в 08:30 (AI), 11:00 (напоминания), 21:00 (отчёт).
5. **Загрузка** в 7707233 (или соответствующий сценарий), сценарий остаётся включён; 5 смоук-кейсов с аккаунта владельца; проверка ошибок за 15 минут.
6. **Откат** (≤ 2 мин): загрузить бэкап из п. 1; если меняли хук — `setWebhook` на прежний URL (инструмент 7706894). Откат проверяется на тестовом боте заранее.
7. Запись в `backup/RESTORE.md`: версия, файл, что изменилось, как откатить.
