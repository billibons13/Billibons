# Lead Hunter v2 — управляемая автономная AI-команда (8 агентов) + SYSTEM GUARDIAN

Задача: T-20261013-0040 · Версия документа: 1 (13.10.2026) · Основа: аудит `AUDIT_2026-10-13_for_ChatGPT.md`.
Метки: [ФАКТ] — проверено · [ПРЕДПОЛОЖЕНИЕ] — проверить при тесте · [ВЛАДЕЛЕЦ] — решение владельца (деньги, цены).

## 1. Цель и принципы

Команда сама ищет реальные заказы, анализирует потребность, оценивает шанс, считает затраты и прибыль, готовит ТЗ и КП
и присылает владельцу одну карточку в Telegram. **Выполнение запускается только кнопкой владельца.**

Принципы, которые не меняются:
1. Агенты предлагают — владелец решает. Клиенту ничего не уходит автоматически: первое сообщение отправляет владелец.
2. Детерминированное делает Make (фильтры, расчёты, статусы). Claude — только там, где нужен смысл текста.
3. Направление поиска хранится в настройках и меняется командой `/search_settings`, а не правкой сценариев.
4. Коммерческие заказы — отдельный трек; свои проекты (RAIV FISH, ADH, Bau, контент) в него не попадают.
5. Любой сбой замечает SYSTEM GUARDIAN раньше владельца.
6. Секреты — только в подключениях Make; в промтах, логах, git и чате их нет.

### 2.1 Конвейер лида и статусы

```
Scout → Gatekeeper ─(отсеян: FILTERED_OUT, без AI, без Telegram)
          │ прошёл
          ▼
LH-03 NEW → LH-10 Analyst → ANALYZED → grade
          │  grade ∉ send_grades → ARCHIVED (без сообщения, видно в /today, /stats)
          ▼  grade ∈ send_grades
Карточка 1 (оценка) → владелец: ✅ Approve | ❌ Reject | 🔍 More
          ▼ ✅ (gate G1)
LH-11 Architect → Sales → Estimator → Карточка 2 (ТЗ + КП + затраты/прибыль + вердикт)
          ▼ владелец: 🚀 В работу (gate G2) | ❌ Lost | 📦 Archive
IN_EXECUTION → чек-лист выполнения, напоминания → 📞 Contacted → 🏆 Won / ❌ Lost
```

Gate G2 «🚀 В работу» ничего не отправляет клиенту. Он переводит лид в `IN_EXECUTION`, присылает владельцу
чек-лист: отправить сообщение клиенту, договориться о цене, создать проект в репозитории. Время фиксируется для статистики.

### 2.2 Estimator — расчёт затрат и прибыли (детерминированно, в Make)

Входы: `estimated_hours_min/max` (Architect), `recommended_price`, `minimum_acceptable_price` (Sales), настройки владельца.

| Величина | Формула | Настройка |
|---|---|---|
| Трудозатраты | `hours_max × internal_rate_eur` | `internal_rate_eur` [ВЛАДЕЛЕЦ], сейчас `sales_hourly_rate_eur` = 35 |
| Комиссия площадки | `recommended_price × platform_fee_pct` | Freelancer 10 % [ПРЕДПОЛОЖЕНИЕ: проверить тариф аккаунта] |
| Инструменты и AI | `ai_cost_lead_eur + tools_cost_eur` | сумма runs по лиду + `tools_cost_eur` [ВЛАДЕЛЕЦ] |
| Резерв на риск | `(трудозатраты) × risk_buffer_pct` | 15 % по умолчанию; ×1,5, если есть risk_flags |
| **Затраты** | сумма четырёх строк | |
| **Прибыль** | `recommended_price − затраты` | |
| **Маржа** | `прибыль / recommended_price` | |
| **Вердикт** | 🟢 GO, если маржа ≥ `min_margin_pct` и цена ≥ `minimum_order_eur`; 🟡 CHECK, если маржа 10 %…min; 🔴 NO-GO | `min_margin_pct` [ВЛАДЕЛЕЦ], предлагается 30 % |

Вердикт — подсказка. Решение всегда за владельцем (кнопка G2 доступна и при NO-GO, с предупреждением).

## 3. `/search_settings` — направление поиска без правки сценариев

### 3.1 Запись `search` в lh_settings (207951)
```json
{
  "version": 1,
  "sources": {"freelancer": true},
  "categories": ["telegram", "chatbot", "make", "ai_chatbot", "bot_dev"],
  "category_jobs": {"telegram": [2380], "chatbot": [2068], "make": [2823], "ai_chatbot": [2917], "bot_dev": [2918]},
  "include_regex": "\\b(telegram|chat ?bots?|bots?|mini ?apps?|make\\.com|integromat|n8n|zapier|webhooks?|automation|automate)\\b",
  "exclude_regex": "translat|garment|instructor|copywrit|chat admin|virtual assistant|data entry|\\bseo\\b|moodle|vertriebspartner|sales partner|voice (call|assistant)",
  "languages": ["en", "de", "ru", "uk", "es"],
  "countries": [],
  "budget_fixed_min_eur": 300,
  "budget_hourly_min_eur": 15,
  "max_bids": 200,
  "window_hours": 12,
  "max_per_run": 5,
  "send_grades": ["HOT", "WARM", "COLD"]
}
```
[ФАКТ] ID категорий Freelancer проверены через API 13.10: 2380 Telegram API, 2068 Chatbot, 2823 Make.com, 2917 AI Chatbot, 2918 Bot Development.
[ФАКТ] Фильтр `jobs[]` работает, но заказчики вешают «Chatbot» на копирайтинг, поддержку и SEO. Исключение по чужим категориям
отрезает и нужные заказы (у «Bot WhatsApp» есть Website Design и Graphic Design), поэтому Gatekeeper работает по тексту:
`include_regex` / `exclude_regex` + язык + бюджет + ставки. Эталон и тест: `scripts/gatekeeper.py`, `scripts/test_gatekeeper.py`
(23 реальных проекта: 23/23 совпали с разметкой, к Analyst прошли 7, вместо 23 без фильтра).
В `/search_settings` владелец правит слова (`add_kw`, `exclude`), Make пересобирает regex через `join(...; "|")`.
[ФАКТ] Страна в ответе API без авторизации пустая (`location.country = {}`), поэтому `countries` пока проверяется только по тексту
(«Germany», «Deutschland», «DACH», город) и валюте. Это слабый признак, в карточке помечается как «страна не подтверждена».
[ФАКТ] Всего активных проектов по 5 категориям — 38 (13.10). Поток на этой площадке маленький, нужен второй источник (этап 6).

### 3.2 Интерфейс в боте (LH-20)
- `/search_settings` — сводка и кнопки: `📂 Категории` `🌐 Языки` `🌍 Страны` `💶 Бюджет` `📨 Что слать` `↩️ Откат`.
- Экран выбора: переключатели с ✅. callback `ss|<поле>|<значение>` (≤ 64 байт), `editMessageText` на месте.
- Текстовые формы: `/search_settings budget 500`, `/search_settings hourly 20`, `/search_settings bids 40`,
  `/search_settings add_kw <слово>`, `/search_settings del_kw <слово>`, `/search_settings exclude <слово>`.
- Валидация: белый список полей; язык ISO-639-1; страна ISO-3166 alpha-2; числа в диапазонах (бюджет 50–100 000, ставки 1–500, окно 1–48 ч,
  за запуск 1–20). Ошибка — ответ с подсказкой, запись не меняется.
- Каждое изменение: копия в `search_prev`, `version + 1`, событие `SEARCH_SETTINGS_CHANGED` в lh_log (поле, было → стало).
- Применяется со следующего запуска Scout (без перезапуска сценариев).

## 4. SYSTEM GUARDIAN

### 4.1 Два уровня

| Уровень | Где | Частота | Что видит | Цена |
|---|---|---|---|---|
| L1 «пульс» | Make, сценарий GD-01 | каждые 3 ч (после своего ключа Anthropic — каждый час) | heartbeat-записи сценариев, Telegram getWebhookInfo, зависшие лиды, бюджет дня | ≈ 6–8 операций за запуск, без AI |
| L2 «аудит» | Claude routine (ежедневная проверка надёжности, расширенная) | раз в день 08:45 + по запросу | Make API: isActive, isinvalid, executions status 3, очереди вебхуков (queueCount), DLQ, кредиты и прогноз, размер хранилищ | 0 кредитов Make (кроме отчёта) |

### 4.2 Heartbeat-протокол
Каждый сценарий конвейера в конце успешного прогона пишет запись `hb_<код>` в lh_settings:
`{"at": now, "status": "ok|error", "count": N, "note": "…"}`. Коды: `hb_lh01` (Scout), `hb_lh03`, `hb_lh10`, `hb_lh11`, `hb_lh20`.

### 4.3 Проверки L1 (GD-01)

| # | Проверка | Порог тревоги | Действие |
|---|---|---|---|
| 1 | Scout жив | `hb_lh01.at` старше `window_hours + 1 ч` | 🛡 тревога «поиск не запускался» |
| 2 | Webhook бота | `pending_update_count > 5` или `last_error_date` за последний час, или url ≠ LH-20 | тревога; url ≠ ожидаемого → кнопка «🔧 Восстановить webhook» (setWebhook только по нажатию) |
| 3 | Зависшие лиды | NEW > 2 ч (не на паузе); APPROVED без architect_json > 1 ч; ANALYZING > 30 мин | тревога со списком lead_id и кнопкой «🔁 Повторить» |
| 4 | Ошибки | лидов в ERROR за сутки ≥ 2 | тревога с error_code |
| 5 | Бюджет AI | расход дня ≥ 80 % `daily_budget_usd` | предупреждение (100 % — уже автопауза LH-10) |
| 6 | Передача данных | лид SENT_TO_TELEGRAM без `tg_message_id` | тревога «карточка не доставлена» |
| 7 | Пауза забыта | `paused = true` дольше 24 ч | напоминание раз в сутки |

Защита от спама: состояние прошлого прогона в записи `guardian_state`. Сообщение уходит только при **смене** состояния
(OK→ALARM, ALARM→OK «✅ восстановлено») и одной строкой в 09:00 «🛡 Всё в порядке · лидов за сутки N · расход $X».

### 4.4 Проверки L2 (Claude routine, Make API)
1. Сценарии из списка `expected_active` активны, `isinvalid = false`. Список намеренно выключенных (`intentionally_off`) — не тревога.
2. Executions за 24 ч: status 3 по каждому сценарию; повтор одной ошибки ≥ 3 раз → задача директору.
3. Вебхуки: `queueCount > 0` дольше 1 ч — данные застряли.
4. Кредиты: остаток, расход за сутки, прогноз даты нуля; < 20 % месяца — тревога владельцу.
5. Хранилища: размер > 70 % лимита → план ротации (lh_log).
6. GD-01 сам жив (`hb_gd01` моложе 4 ч) — «сторож сторожа».

### 4.5 Что Guardian может делать сам (белый список)
- L2: `scenarios_activate` только для сценария из `expected_active`, если он выключился **не владельцем**
  (в executions нет события stop от аккаунта владельца). Остановленное владельцем не включать никогда.
- L1/L2: восстановить webhook бота — только по кнопке владельца.
- Ничего не удаляет, не меняет логику, цены, настройки поиска, данные лидов, не пишет клиентам.

## 5. Инструкция технического мониторинга (runbook)

| Сигнал | Где смотреть | Норма | Если не норма |
|---|---|---|---|
| Сценарий выключен | Make → Scenarios, L2 | все из `expected_active` ON | проверить, кто выключил (History → stop). Владелец — оставить; иначе — включить, найти причину |
| Ошибки выполнения | Make → сценарий → History (status Error) | 0 за сутки | открыть выполнение, модуль с ошибкой; Telegram 429 — подождать; AI-ошибка — повторить кнопкой; данные — исправить, переиграть (Replay) |
| Очередь вебхука | Make → Webhooks → queue | 0 | сценарий выключен или падает — включить или исправить, очередь обработается |
| Telegram webhook | GD-01, getWebhookInfo | pending 0, без last_error | url не тот — восстановить (кнопка); 401 — токен отозван, нужен новый токен в подключении Make (делает владелец) |
| Зависшие лиды | `/today`, GD-01 | нет NEW > 2 ч | `/resume`; повтор по кнопке; ERROR — смотреть `error_code` |
| Расход AI | `/settings`, lh_settings `day_*` | < 80 % бюджета | разобраться, какой агент тратит (lh_log runs) |
| Кредиты Make | Organization → Usage, L2 | хватает до сброса | снизить частоту Scout/Guardian, свой ключ Anthropic, докупка — решает владелец |
| Хранилища | Data stores | < 70 % | ротация lh_log старше `cleanup_days` (архив в файл, потом очистка — только с «да» владельца) |

Порядок при инциденте: 1) Guardian присылает 🛡 тревогу → 2) директор диагностирует по runbook → 3) чинит только из белого списка
или готовит исправление → 4) владельцу — что случилось, что сделано, что нужно от него → 5) запись в director_log.md.
